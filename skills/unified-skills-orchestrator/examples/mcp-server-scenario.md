User needs to create an MCP server for database operations that must handle concurrent requests efficiently.

### Step 3: Execution Flow

#### Phase 1: Evidence Foundation
```

Output:
- Efficiency = requests per second (RPS)
- Baseline: Current manual operations = 10 ops/minute
- Target: 100+ operations/second (600x improvement)

```

#### Phase 2: MCP Server Implementation
```
Skill: mcp-server-development
Action: Build the database operations server
Output:

- Tools implemented:
  - query: Execute SELECT statements
  - insert: Add records
  - update: Modify records
  - delete: Remove records
  - transaction: Batch operations

```

#### Phase 3: Performance Debugging
```
Skill: distributed-systems-debugging
Action: Profile and optimize the server
Output:
- Bottleneck found: Synchronous database writes
- Solution: Implement write batching
- Trace analysis: 73% time in I/O wait
- Optimization: Add connection pooling
- Load test results: 147 RPS achieved
```

#### Phase 4: Validation
```
Skill: evidence-based-validation
Action: Verify performance claims
Output:
- Measured RPS: 147 (target was 100+) ✓

- Memory usage: 127MB steady state
```

## Decision Points

### Decision 1: Synchronous vs Asynchronous
**Context:** MCP server blocked on database operations

**Orchestrator Resolution:**
1. Evidence skill: Measure impact (43 RPS sync vs potential async)
2. MCP skill: Implement async/await patterns
3. Debug skill: Verify no race conditions
4. Result: 3.4x performance improvement

### Decision 2: Caching Strategy
**Context:** Repeated queries consuming resources

**Orchestrator Resolution:**
1. Debug skill: Identify repeated query pattern (67% cache-able)
2. MCP skill: Implement LRU cache
3. Evidence skill: Measure memory vs performance trade-off
4. Result: 40% RPS improvement for 24MB memory

class DatabaseMCPServer {
  constructor() {
    // Performance validated: 147 RPS

    // Memory validated: 24MB cache overhead
    this.cache = new LRUCache({ max: 1000 });

## Orchestrator Insights

1. **Performance Claims Require Measurement**: Never accept "efficient" without metrics
2. **Implementation Before Optimization**: Build first, measure, then optimize
3. **Debugging Reveals Reality**: Theoretical performance ≠ actual performance
4. **Validation Closes Loop**: Ensures claims match reality
5. **Documentation Prevents Drift**: Record actual, not aspirational metrics
